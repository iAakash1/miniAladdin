# EXP-007 — Staged model search

**Status: PRE-REGISTERED. NOT YET RUN.**

Everything below section 12 is a declared plan with the result fields left
empty. They are filled by `experiments/EXP-007/search.json` and
`artifacts/experiments/EXP-007/final_selection.json` after the run, and by
nothing else. A number in this document that is not in one of those two files
is a fabrication; there are none.

## 1. Why this experiment exists

Every study before this one fixed the model ladder and varied one thing.
EXP-004 asked whether any of seventeen fixed configurations beat free factors.
EXP-005 asked whether four additional data sources add information. EXP-006
asked whether the C_base feature set is tradeable.

None of them asked whether the *ladder itself* was the limit. EXP-006's winner,
`gradient_boosting`, ran on sklearn's defaults — 100 trees, depth 3, learning
rate 0.1 — because that is what `default_specs` declares. It cleared three gates
of four and failed net Sharpe at −0.102. It is a fair question whether a
configuration that was never chosen is the best that family can do.

This experiment asks that question under control. It searches families,
hyperparameters, feature arms and targets in four staged rounds, logs every
configuration, and counts all of them against the cumulative multiple-testing
budget.

## 2. The thing that makes this dangerous, and what stops it

A search of 879 configurations will find something that looks good. That is not
a risk of the method, it is a certainty of it: the maximum of 879 draws from a
zero-skill population is large. The best of 1,035 cumulative zero-skill trials
would be expected to show |t| ≈ 3.39.

So the search pays for its own size. Three mechanisms, all fixed before the run:

1. **`prior_evaluations = 156`** — every trial from EXP-001 through EXP-006
   still counts. The register does not reset because the code changed.
2. **The `survives_search_size` gate** — the winner's |t| must exceed the
   expected maximum |t| of a zero-skill population of the same cumulative size.
   This gate did not exist in earlier studies because they did not search.
3. **The budget is printed before the run.** `python -m src.quant.train
   --experiment EXP-007 --budget overnight --performance max` prints the trial count and the
   resulting bar as part of the dry run. Choosing `overnight` over `standard`
   is choosing to raise the bar from 3.09 to 3.39 in exchange for more
   configurations.

A larger search cannot lower the bar. It is the only honest way to run one.

## 3. What is being searched

| Stage | What varies | What is held | Configurations (overnight) |
|---|---|---|---|
| 1 SCREEN | family, coarse hyperparameters | arm `C_base`, target `fwd_rank_21` | 129 |
| 2 TUNE | hyperparameters, in the families that survived | arm, target | 630 |
| 3 CONTEXT | feature arm x target, at each finalist's fixed hyperparameters | hyperparameters | 60 |
| 4 ROBUSTNESS | small perturbations around each finalist | arm, target | 60 |
| | | | **879** |

Stage 1 decides where Stage 2's budget goes. Spending it flat would tune
families the screen already showed are not competitive — 630 configurations
spread over eight families is 79 each, and the four that matter would get a
quarter of the search they deserve.

Stage 4 exists because a winner that is a single point in hyperparameter space
and a winner that sits in a region of comparable configurations are different
claims. If a finalist's ten neighbours are all far worse, the finalist is a
draw from the tail, not a setting.

## 4. Search spaces

Declared in `src/quant/study/search.py::SPACES`, one `Axis` per hyperparameter,
sampled deterministically from `(family, stage, seed)`. Re-running with the same
seed produces the same configurations, which is what makes `--resume` safe: a
resumed run continues the same search rather than starting a correlated new one.

Eight families: `gradient_boosting`, `hist_gradient_boosting`, `random_forest`,
`extra_trees`, `ridge`, `lasso`, `elastic_net`, `ols`.

`ols` carries one configuration because it has no hyperparameters. It is in the
search as the linear overfitting control, exactly as it is in `default_specs`.

## 5. Feature arms and targets

Stage 3 sweeps five arms x two targets. Arms come from
`src/quant/study/families.py::DEFAULT_ARMS`, whose membership is derived from
the feature registry's declared groups rather than hand-listed, so an arm
cannot silently drift from the family it names.

Targets are `fwd_rank_21` (primary, declared before any result was seen) and
`fwd_ret_21`.

## 6. What is NOT searched

- **Costs.** The 10 bp half-spread is not a tunable. EXP-006 established that
  its net Sharpe crosses zero between 5 and 10 bp; searching the cost
  assumption would be selecting the assumption that makes a model pass.
- **Execution lag.** Fixed at 1 rebalance period. `ExperimentDefinition`
  refuses anything lower.
- **Fold geometry.** Purge, embargo, validation length and minimum training
  length are the same as every prior study on these folds. Changing them would
  make the cumulative trial count meaningless.
- **Gate thresholds.** They are in code, they are the same as
  `ModelRegistry.CANDIDATE_THRESHOLDS`, and the search cannot reach them.
- **The holdout.** See section 11.

## 7. The gates

Eight, in `src/quant/study/heavy.py::evaluate_gates`. None move.

| Gate | Requirement |
|---|---|
| `ic_t_stat` | \|t\| ≥ 2.0 |
| `gross_sharpe` | > 0 |
| `net_sharpe` | > 0 at the declared 10 bp half-spread |
| `beats_best_baseline` | IC above the best baseline **refit on the same folds and label** |
| `not_overfit` | train − validation IC ≤ 0.15 |
| `survives_search_size` | \|t\| > the expected max \|t\| of the cumulative trial count |
| `alpha_credible` | six-factor alpha t > 0 |
| `turnover_tolerable` | ≤ 30x annualised |

The verdict is binary and unweighted. A composite score would invite tuning the
weights until the preferred configuration wins.

**Passing all eight yields DEVELOPMENT CANDIDATE, not a production model.**
Production requires the holdout, which this study does not spend.

## 8. NO PRODUCTION CANDIDATE is an expected outcome

EXP-004 found no learned model beating free factors. EXP-005 found no
additional data source adding information. EXP-006 found one model that clears
three gates of four and fails on cost. The prior that a hyperparameter search
turns that into a passing model is not high.

If nothing clears the gates, the result is recorded as NO PRODUCTION CANDIDATE
and the gates are not adjusted. That outcome is worth the compute: it converts
"we used defaults" into "we searched 879 configurations and the ceiling is
still below the cost line", which is a materially stronger statement.

## 9. Reproducibility

- Configurations are a deterministic function of `(family, stage, index, seed)`.
- Worker count does not affect results. `validation/parallel.py` sorts outcomes
  back into declared spec order before returning, because completion order
  depends on the pool size and CSCV partitions columns in insertion order —
  without the sort, the reported PBO could change with `--workers` alone. This
  was verified: a 6-worker and a 7-worker run of EXP-006 produced bit-identical
  metrics.
- Threads per worker is pinned to 1 in **every** performance policy. Multi-
  threaded BLAS can reorder reductions and change the last bits of a linear fit;
  if the thread count varied by policy, `--performance max` could produce a
  different number from `safe`.
- `select_candidate` refits each finalist and records `search_mean_ic` against
  `refit_mean_ic`. A non-zero delta means the run is not reproducible and the
  selection should not be trusted.

## 10. Crash safety

Every completed configuration is appended to
`experiments/EXP-007/checkpoints/configs.jsonl` immediately, as JSONL, append
only. A crash mid-write costs one line, which the reader skips with a warning,
rather than truncating a rewritten file.

`--resume` loads the checkpoint and skips what is recorded. Nothing is refit and
no result changes, because configurations are deterministic in the seed.

## 11. The holdout

Not read. Not armed. Not used for selection.

`build_plan` reserves the final 252 sessions before the first fold is cut.
`HoldoutFirewall.assert_clear` runs on the training frame **and** the validation
frame of every fold immediately before every fit — several hundred times over
this run. There is no environment variable that disables it;
`_env_override_is_refused` raises if `QUANT_DISABLE_HOLDOUT_FIREWALL` is set, so
the flag is worse than useless to anyone who finds it.

The training command has no code path that opens the holdout. Spending it
requires `python -m src.quant.study.holdout` under the contract in
`docs/HOLDOUT_CONTRACT.md`.

## 12. Running it

```bash
python -m src.quant.train --experiment EXP-007 --budget overnight --performance max --confirm
```

Dry run — the default, without `--confirm` — prints the machine profile, the
worker plan, the four stages, the projected wall time and the multiple-testing
cost, and fits nothing.

After an interruption:

```bash
python -m src.quant.train --experiment EXP-007 --budget overnight --performance max --confirm --resume
```

Then:

```bash
python -m scripts.quant.select_candidate --experiment EXP-007
```

Full operational detail is in [training.md](training.md).
